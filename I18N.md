# PedigrAPP — English/Spanish internationalization

## Version 1.2: overview and scope

PedigrAPP is **one bilingual application**, not two copies of its source. It uses centrally maintained ES/EN dictionaries without runtime machine-translation services. The user can switch languages instantly while editing a family; the operation must never alter clinical data, relationship identifiers, layout geometry, or Undo/Redo history.

Version 1.2 uses JSON schema 4.22. The public distribution includes the locale bundle generator. Internal translation validators and their registries are not distributed. Regression fixtures and internal validation reports are not distributed. Automated checks do not replace browser and target-server acceptance testing.

## Architecture

- `locales/es.json` and `locales/en.json` are the **editable sources of truth** (UTF-8 JSON). Both dictionaries must contain exactly the same semantic keys and equivalent interpolation parameters.
- `scripts/build_locale_bundle.py` generates `locales/catalog.js`. This generated file makes both languages available **before the editor builds its dynamic UI**, avoiding late-loading English text. Do not edit the generated catalog by hand.
- `i18n.js` exposes the common translation function `t(key, params)` and the localization interface `current()`, `setLanguage('es'|'en')`, `apply()`, and `init()`.
- Parameters use named placeholders such as `{name}`. If a required English translation is unavailable, Spanish is used as a fallback, with a developer-console warning.
- Spanish is the default. The preference is stored in `localStorage['pedigrapp.language']` and the document's `<html lang>` follows the active language.
- HTML supports `data-i18n="key"`, `data-i18n-title`, `data-i18n-placeholder`, and `data-i18n-aria-label`. New dynamic JavaScript UI strings must use `t('domain.action')` and should be refreshed when the locale changes.
- No external translation API or new frontend framework is required.

**Preserve the data model.** Record types (`stillbirth`, `fetus`, etc.), relationship types, UID, genetic codes, patient-entered names, descriptions, molecular variants, and free clinical notes are data, not translations. Localize *their automatically generated labels*, not the stored values.

## Adding a new UI string: required workflow

1. Choose a stable semantic key, for example `action.undo`, independent of the visible text or the element position.
2. Add the same key to **both** `locales/es.json` and `locales/en.json` with clinically appropriate translations. Keep interpolation placeholders identical.
3. Reference the key from JavaScript via `t('action.undo')`, or from HTML via the relevant `data-i18n-*` attribute.
4. For dynamically managed controls (e.g., Save with pending changes, Undo count, reviewed status), translate inside the function that updates the control, and rerun that function when the language changes. A static `data-i18n` attribute would overwrite its state-specific label.
5. Do not add a static `data-i18n` attribute to clinical headings containing a patient name, identity, genotype, or other live data. Translate the UI fragments while preserving the entered values.
6. Regenerate the catalog and run the checks below. Test ES → EN → ES with the relevant control open and unsaved data present.
7. Document terminology decisions when they are clinically significant, particularly in adoption, assisted reproduction, sex/gender terminology, and carrier status.

Version 1.2 includes bilingual death-year labels, clinical-provenance disclosure, PED safety warnings, reproductive QC, and partner-creation actions. Clinical values entered by users remain unchanged.

**Project-wide rule:** Every new feature with visible UI content must include its **Spanish and English translations in the same change**. This includes tooltips, notifications, dialogs, accessibility labels, help, QC, PDF/print output, and error handling.

### Regenerate the locale bundle

```bash
python3 scripts/build_locale_bundle.py
python3 scripts/build_locale_bundle.py --check
```

Before a release, validate matching ES/EN keys, interpolation placeholders, references, and the generated catalog. Test language switching, family persistence and export using synthetic data. Internal validation scripts and their reports are deliberately excluded from the public package.

## Test coverage and remaining limits

ES/EN dictionary parity, placeholders, references, generated catalogs, and reviewed literal exceptions are checked automatically. Interactive browser behavior, mobile rendering, exports, and deployment access controls require acceptance testing. The private regression fixtures are intentionally excluded from the public distribution.

## Publication and documentation

GitHub-facing Markdown documentation is in English to make the project easier for international contributors to discover and evaluate. **Do not translate the official registered Spanish software title, authors' personal names, license text, rights holder's legal name, identifiers, or scientific citations.** Translating repository documentation does not publish a local build to GitHub or Zenodo.

## Schema and clinical data

The stable v1.2 data schema is 4.22. Preserve user-entered names, dates, provenance, clinical notes, and variant descriptions verbatim when changing the interface language. PED SEX must not be used to infer gender identity. Clinical-provenance dates are stored as ISO calendar dates; export generation time is independent.
