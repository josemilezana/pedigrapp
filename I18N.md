# PedigrAPP — English/Spanish internationalization

## Version 1.0.5: overview and scope

PedigrAPP is **one bilingual application**, not two copies of its source. It uses centrally maintained ES/EN dictionaries without runtime machine-translation services. The user can switch languages instantly while editing a family; the operation must never alter clinical data, relationship identifiers, layout geometry, or Undo/Redo history.

Version 1.0.5 was prepared from the reviewed `v1.0.5-rc8` candidate. Automated parity, browser, and synthetic-data regression checks passed in the rc8 review. **Hosting-layer access control and physical-phone testing were not part of the automated package validation.** The test scope and remaining limitations are summarized below under *Test coverage and remaining limits*.

## Architecture

- `locales/es.json` and `locales/en.json` are the **editable sources of truth** (UTF-8 JSON). Both dictionaries must contain exactly the same semantic keys and equivalent interpolation parameters.
- `scripts/build_locale_bundle.py` generates `locales/catalog.js`. This generated file makes both languages available **before the editor builds its dynamic UI**, avoiding late-loading English text. Do not edit the generated catalog by hand.
- `i18n.js` exposes the common translation function `t(key, params)` and the localization interface `current()`, `setLanguage('es'|'en')`, `apply()`, and `init()`.
- Parameters use named placeholders such as `{name}`. If a required English translation is unavailable, Spanish is used as a fallback, with a developer-console warning.
- Spanish is the default. The preference is stored in `localStorage['pedigrapp.language']` and the document's `<html lang>` follows the active language.
- HTML supports `data-i18n="key"`, `data-i18n-title`, `data-i18n-placeholder`, and `data-i18n-aria-label`. New dynamic JavaScript UI strings must use `t('domain.action')` and should be refreshed when the locale changes.
- No external translation API or new frontend framework is required.

**Preserve the data model.** Record types (`stillbirth`, `fetus`, etc.), relationship types, UID, genetic codes, patient-entered names, descriptions, molecular variants, and free clinical notes are data, not translations. Localize *their automatically generated labels*, not the stored values.

## Adding a new UI string: required workflow

1. Choose a stable semantic key, for example `action.undo`, independent of the visible text or the element position.
2. Add the same key to **both** `locales/es.json` and `locales/en.json` with clinically appropriate translations. Keep interpolation placeholders identical.
3. Reference the key from JavaScript via `t('action.undo')`, or from HTML via the relevant `data-i18n-*` attribute.
4. For dynamically managed controls (e.g., Save with pending changes, Undo count, reviewed status), translate inside the function that updates the control, and rerun that function when the language changes. A static `data-i18n` attribute would overwrite its state-specific label.
5. Do not add a static `data-i18n` attribute to clinical headings containing a patient name, identity, genotype, or other live data. Translate the UI fragments while preserving the entered values.
6. Regenerate the catalog and run the checks below. Test ES → EN → ES with the relevant control open and unsaved data present.
7. Document terminology decisions when they are clinically significant, particularly in adoption, assisted reproduction, sex/gender terminology, and carrier status.

**Project-wide rule:** Every new feature with visible UI content must include its **Spanish and English translations in the same change**. This includes tooltips, notifications, dialogs, accessibility labels, help, QC, PDF/print output, and error handling.

### Required commands before every new version

From the application root:

```bash
python3 scripts/build_locale_bundle.py
python3 scripts/check_i18n.py --gate
python3 scripts/check_i18n.py --strict
python3 scripts/audit_untranslated.py
for test in tests/*.test.js; do node "$test"; done
```

Browser tests may additionally be run when Python, Playwright, and Chromium are available:

```bash
python3 tests/i18n-bilingual.browser.py
```

Run targeted browser regressions for newly added UI actions as well as QC, clinical cards, family save/load, responsive layouts, and exports. For the static online edition, independently check browser `localStorage` persistence, hosting access controls where applicable, and PDF output in the target browsers.

## What the validators enforce

- `scripts/check_i18n.py` checks dictionary parity, nonempty translations, duplicate keys, missing references, interpolation placeholders, and generated-catalog freshness.
- `--gate` compares new JavaScript text against `scripts/i18n_literal_baseline.json`, preventing **new unreviewed literals**. It also blocks growth of provisional keys such as `legacy.ui_*` or `app.body1.*`.
- `--strict` additionally checks the reviewed-exceptions registry `scripts/i18n_reviewed_exceptions.json`: unexplained new candidates and outdated exceptions must be reviewed.
- `scripts/audit_untranslated.py` produces a heuristic text audit. Some findings are false positives: technical identifiers, scientific references, original Spanish source messages used by QC fallback, or proper names.

**These checks prevent regression but do not mathematically prove that every possible runtime string is translated.** The change author must also check the actual interface and terminology. The inherited `legacy.ui_*` keys are migration scaffolding: do not add new ones, and progressively replace existing ones with semantic keys.

Never update the literal baseline automatically just to make failing tests pass. Review each finding, document legitimate exceptions, and update the baseline deliberately if the review warrants it.

## Scientific terminology

Follow the cited Bennett/NSGC pedigree nomenclature recommendations (1995, 2008, 2022) and the **2025 correction** when applicable. Maintain the distinction between **gestational carrier** (carries a pregnancy without providing the oocyte) and **surrogate** (provides the oocyte and carries the pregnancy), consistent with the application's reference conventions. Keep established abbreviations such as **SAB, TOP, ECT, AMAB, AFAB, UAAB** where appropriate.

Never change relationship types, clinical rules, or the pedigree geometry as part of translation work.

## Implementation notes and lessons from release candidates

- **rc2:** Added flag-labelled language switching and keyed QC/help data. QC details are translated when calculated; changing languages refreshes the displayed QC without changing family history.
- **rc3:** Extended translation of editor messages and help history. Help changelog, symbol groups, and relation labels use stable identifiers rather than array positions. Introduced an incremental literal guard.
- **rc4:** Introduced synchronous `locales/catalog.js` built from editable JSON sources, avoiding late translation on initial page load. The i18n module must load before `pedigree.js` and `help.js`.
- **rc5:** Added state-aware toolbar labels, condition options, and clinical cards. Some user-editable form headings must be refreshed **in place** to preserve unsaved data.
- **rc6:** Localized empty-state viewer text, condition-sector legends, search, saved-case counters, and lists. Data-dependent elements use `data-i18n-managed="true"` where needed so static translation does not overwrite their values.
- **rc7:** Localized clinical summaries and tooltip relationship menus, including when expanded. Automatically generated fetal, gestational-carrier, and donor labels are translated in QC; user-entered aliases are preserved. QC identifiers such as `GEST_AGE` do not change.
- **rc8:** Localized contextual QC parameters such as union, parentage, parents, sibship, and multiple gestation. Reviewed the remaining audit exceptions, and restored older browser tests to load i18n before the editor.

## Test coverage and remaining limits

The rc8 review verified 1,570 translation keys per language, strict validation, eight Node.js tests, 19 example pedigrees, contextual interactions, English/Spanish PDF generation with a fictitious clinical case, and stable geometry/JSON during language switching. A physical mobile device, the hospital's actual Apache/PHP deployment, and historical clinical records were not tested in that review. These require manual acceptance tests and must not be described as automatically verified.

## Publication and documentation

GitHub-facing Markdown documentation is in English to make the project easier for international contributors to discover and evaluate. **Do not translate the official registered Spanish software title, authors' personal names, license text, rights holder's legal name, identifiers, or scientific citations.** Translating repository documentation does not publish a local build to GitHub or Zenodo.
